# spec 024 — 워크스페이스 수명주기 (보관·삭제·중복 예방)

> 상태: **논점 확정 완료(2026-07-27) — 구현 대기.** 조사·근거는 `notes.md`(기획 검토 노트) 참조.
> 작성: 다온 · 확정: 대표 (A·B·D 추천안 채택, C 축소, E 신설)

## 0. 목표 우선순위 (대표 확정)

1. **EO 사용자들이 Carelog로 자연스럽게 이행되는 흐름을 최우선한다.**
2. 안 쓰는 Carelog 계정(워크스페이스·개인 계정)이 묵혀 있지 않도록 한다.
3. 같은 의료기관의 워크스페이스가 중복 생성되는 것을 막는다.

## 1. 구조적 사실 (설계의 전제)

- **EO 경유로는 중복이 생기지 않는다.** EO는 클리닉당 연동 링크 1개(`workspace_integrations`)이며, 모든 직원의 SSO 토큰에 같은 institution_id가 실린다. Carelog SSO는 그 id로 upsert(`ignoreDuplicates`) — 직원 몇 명이 눌러도 같은 워크스페이스에 멤버로 붙을 뿐이다(`app/api/auth/sso/route.ts` 1-b).
- **중복의 원천은 셀프 가입 경로다.** EO를 거치지 않고 이메일/Google로 직접 가입하면 온보딩이 새 워크스페이스 + owner를 만든다.
- **DB 안전망**: `patient.institution_id`·`consultation.institution_id`는 cascade가 없어, 환자·상담 기록이 1건이라도 있는 기관은 hard DELETE가 FK로 거절된다. **이 안전망은 유지하고 우회하지 않는다.**
- **EO 연동 기관은 지워도 되살아난다**(좀비 부활): 직원이 "케어로그 열기"를 누르면 SSO가 같은 id로 재생성. → Carelog에서 지우는 행위 자체가 무의미.

## 2. 확정 결정

| # | 논점 | 결정 |
|---|---|---|
| A | 삭제 권한 | **슈퍼어드민(대표) 전용.** owner 셀프 삭제는 후속(§7.2 정리 도구). |
| B | 삭제 방식 | **soft 보관(archive) 기본 + "빈 기관"(환자 0·상담 0)만 즉시 hard delete.** FK 안전망 유지. |
| C | EO 연동 기관 | **삭제 차단만 한다(장치 없음).** "EO 연동 기관" 뱃지 + 차단 안내. 링크 해제는 EO 측(SSOT) 기능이므로 Carelog가 만들지 않는다 — 놔둬도 손해(용량·비용)는 무시 가능한 수준이며, 리스크는 오직 '중복 존재 시 혼선'뿐이고 그건 E(원천 예방) + A/B(잔재 정리)로 막는다. |
| D | 데이터 있는 기관 | **이관은 v1 제외.** "비우기 전엔 못 지움"이 안전. 기관 간 데이터 이관은 별도 스펙. |
| E | 중복 예방(신설) | **온보딩에서 원천 차단.** v1은 안내 카피("병원이 EO를 쓰고 계시면 새로 만들지 말고 EO에서 '케어로그 열기'로 시작하세요"). v2(조건부)는 가입 이메일이 EO 연동 기관 직원 명부에 있으면 새 생성 대신 기존 워크스페이스 안내 — **EO 마스터 동기화 데이터에 이메일 포함 여부 확인 선행.** |

## 3. 기능 요구사항 (v1)

### FR-1. 슈퍼어드민 기관 관리 (/admin 기관 카드)
- **보관(soft)**: `institutions.archived_at` 설정 → 워크스페이스 전환 목록·홈에서 숨김. 복원 가능.
- **삭제(hard)**: 빈 기관(환자 0·상담 0)만 노출. DB FK 안전망이 최종 방어선.
- **EO 연동 뱃지 + 삭제·보관 차단**: EO가 링크한 기관(연동 여부는 gateway/sync 데이터로 판별)은 보관·삭제 모두 차단 — SSO 재생성과 충돌하므로.
- **삭제 전 요약 다이얼로그**: 멤버 n · 환자 n · 상담 n 표시 + 기관명 재입력 확인.
- **감사 기록**: activity_logs에 보관/복원/삭제 기록.
- **기관명 수정(슈퍼어드민)**: 현행 owner 전용(`updateInstitutionName`)과 별도로 /admin에서 수정 가능(EO 기관은 owner가 없어 아무도 못 바꾸는 문제 해소).

### FR-2. 보관(archive) 동작 정의
- 마이그레이션: `alter table institutions add column archived_at timestamptz;`
- 보관된 기관: 전환 UI·기관 선택에서 제외, active 쿠키가 가리키면 다른 기관으로 폴백(없으면 온보딩).
- 데이터·멤버십은 그대로 보존(RLS 접근은 유지하되 UI에서 숨김) — 복원 시 즉시 원상.

### FR-3. 가드
- 사용자의 마지막 기관을 보관/삭제하면 무기관 상태 → 온보딩 폴백 검증.
- active institution 쿠키 stale 정리(미들웨어/전환 UI).

### FR-4. 온보딩 중복 예방 (E)
- v1: "새 워크스페이스 만들기" 단계에 EO 안내 카피 추가.
- v2(후속): 이메일 ↔ EO 직원 명부 대조 → 기존 워크스페이스 안내. (EO 마스터에 이메일 필드 확인 후 착수)

## 4. 범위 제외 (v1)

- owner 셀프 삭제·정리 도구, 기관 간 데이터 이관, EO 링크 해제/재지정(EO 측 기능), 개인 계정(auth user) 삭제.

## 5. 당면 케이스 — 중복 워크스페이스 정리 ✅ 완료 (2026-07-28, SQL 수동 처리)

진단 결과와 처리 내역 (코드 배포 없이 SQL로 해결):

- **원인 규명**: EO 예미안 워크스페이스의 carelog 링크가 6/28 재연동 과정에서 **새 UUID로 재발급**되어(카드 #621 가드 이전), 빈 워크스페이스 `예미안치과의원(734b610d)`이 SSO로 자동 생성됨. 이후 신규 SSO 직원 4명이 빈 쪽으로 합류(전원 정본에도 멤버십 보유 — 손실 0 확인).
- **처리**: ① EO `workspace_integrations`의 carelog external_id를 정본 `예미안치과(0e4e85d6)`으로 UPDATE(재지정) → ② Carelog에서 빈 중복(`734b610d`) + 시드 잔재(`기본 의료기관 a0000000…`) + 테스트(`d d865efc5…`) 3건 hard delete.
- **교훈 → E 논점 근거**: EO 슈퍼어드민 케어로그 토글은 OFF→ON 시 externalId 재발급 구멍이 있음(재연결 시 기존 id 복원 안 됨) — **EO 측 수정 요청 카드 헤임달 전달**(§5.1). Carelog 온보딩 예방(E)과 별개로 EO 쪽 원천도 막아야 함.

### 5.1 헤임달(EO) 전달 카드 — 케어로그 토글 재발급 구멍

- 증상: `/api/superadmin/integrations` POST는 기존 행 있으면 external_id 보존(#621)하지만, **DELETE 후 재-POST는 새 UUID 발급** → 위성(Carelog)에 유령 워크스페이스 생성.
- 요청: ① 재연결 시 직전 external_id 복원(soft delete 또는 이력 테이블) ② (운영용) externalId 수동 입력 옵션 — 1:1 중복 가드는 이미 있음 ③ 토글 OFF 시 "재연결 시 새 ID가 발급됩니다" 경고 카피.
